# Meowv Studio 迁移计划

## 1. 决策与目标

本计划的目标不是为现有站点增加一个聚合入口，而是最终交付一个新的单体前端应用
**Meowv Studio**：图片、Markdown、PDF 与 Office 四类能力均在 `studio/` 中实现，用户在同一
域名、同一导航和同一应用壳内通过不同路由使用功能。

这是一项**产品重构**，不是旧代码的搬运工作。Studio 必须围绕统一的用户任务、产品信息架构、
交互体验、性能与本地隐私边界重新设计；旧项目仅作为功能需求和行为验证的参考来源。对不符合
目标架构、重复、难维护或体验不佳的旧实现，应先识别问题，再按 Studio 的规范重新实现，而非
原样迁入。

建议目标地址为 `studio.meowv.com`。现有 `img.meowv.com`、`md.meowv.com`、
`pdf.meowv.com` 与 `office.meowv.com` 在迁移、验收和回滚期继续保留；在 Studio 完成上线
验证前，不删除、移动或重写它们。

本次统一的范围为：

- `image/` 的浏览器本地图片处理能力；
- `markdown/` 的本地 Markdown 工作台与导出能力；
- `pdf/` 的浏览器本地 PDF 工具；
- `office/` 的本地 OnlyOffice 文档编辑能力。

`blog/`、`excel/` 与 `zitie/` 不在本次迁移范围内。尤其 `excel/` 是 Office 的现有回滚基线，
迁移完成前不得改动其项目位置或代码。

## 2. 目标技术方案

### 2.1 统一技术栈

Studio 统一采用下列技术方案：

| 层级 | 目标选择 | 说明 |
| --- | --- | --- |
| 应用框架 | Vue 3 + Vite + Vue Router | Image、Markdown 与 Office 已使用 Vite；Studio 是浏览器本地工具站，以纯客户端路由和静态产物统一四项能力，迁移阻力最低。 |
| 语言 | TypeScript（严格模式） | 新增和迁入模块必须保留或补齐严格类型。 |
| 包管理 | pnpm | Studio 内只维护一个锁文件与一组根命令。 |
| 构建与发布 | Vite 静态构建 | 在本地构建 `studio/dist/` 后手动部署，不引入后端、托管构建或 CI 发布。 |
| 组件与样式 | Vue 组件 + Studio 设计令牌 | 按统一布局、颜色、间距、图标、弹窗、空状态与无障碍规范重构产品体验。 |
| 验证 | 类型检查、Lint、格式检查与浏览器验收 | 不迁移旧项目测试代码、夹具或报告；以 Studio 的功能验收标准验证最终实现。 |

Studio 是纯客户端静态应用。所有涉及 File System Access API、IndexedDB、Worker、Canvas、
Object URL、OnlyOffice iframe 与 WASM 的功能均必须在 Vue 组件的客户端生命周期中初始化，
并在路由离开和组件卸载时销毁。

### 2.2 目标目录

```text
studio/
├── src/
│   ├── pages/                 # Studio 首页和四个功能路由
│   ├── router/                # Vue Router 路由定义与路由守卫
│   ├── layouts/               # 统一应用壳、导航和页脚
│   ├── components/            # Studio 通用组件
│   ├── composables/           # 路由、任务和浏览器能力编排
│   ├── features/
│   │   ├── image/             # 图片功能迁入模块
│   │   ├── markdown/          # Markdown 功能迁入模块
│   │   ├── pdf/               # PDF 功能迁入模块
│   │   └── office/            # Office 功能迁入模块
│   ├── assets/                # 统一样式与设计令牌
│   └── core/
│       ├── browser/           # 文件、Worker、对象 URL、能力检测与清理
│       ├── privacy/           # 本地处理和数据保留策略
│       └── shared/            # 无 UI 的通用类型、错误和工具函数
├── public/
│   └── office-assets/         # OnlyOffice、字体、x2t WASM 等同源静态资源
├── package.json
├── pnpm-lock.yaml
└── vite.config.ts
```

Office 的大体积静态资源必须使用 `office-assets/` 这类专属前缀，不能占用 `/office/` 路由或与
其他功能的 `assets`、Worker、manifest、favicon 发生冲突。

Studio 不迁移旧项目的 README、设计稿、历史迁移说明、测试代码、测试夹具、覆盖率报告、截图、
无用脚本和非功能性资源。只有运行最终功能不可缺少的代码、依赖、字体、WASM、编辑器资源与
依法必须保留的第三方许可声明可以进入 Studio；其中 Office 的许可证、上游归属与版本信息属于
合规必需内容，不视为可删除的旧文档。

### 2.3 路由与产品信息架构

| 路由 | 名称 | 首期范围 |
| --- | --- | --- |
| `/` | Meowv Studio | 工作台首页、四类工具入口、隐私承诺和最近任务入口。 |
| `/image` | 图片处理 | 保留现有图片处理工具；按工具拆分子路由。 |
| `/markdown` | Markdown 工作台 | 工作区、编辑、预览、搜索、图谱与本地导出。 |
| `/pdf` | PDF 工具 | 现有 PDF 工具页及隐私、帮助等说明页。 |
| `/office` | Office 文档 | 新建、打开、编辑、保存 DOCX、XLSX、PPTX、CSV。 |
| `/privacy` | 隐私说明 | 统一说明本地处理边界，并链接到各功能的差异说明。 |
| `/help` | 帮助 | 浏览器兼容性、权限、文件格式和故障排查。 |
| `/donate` | 捐赠 | 独立展示支持方式、用途说明与致谢；不在 Studio 内处理支付或保存支付信息。 |

首页只负责发现与跳转，不预加载 PDF.js、Monaco、OnlyOffice、x2t WASM 或任何大型编辑器依赖。
各功能路由必须按需加载自身代码、Worker、字体和静态资源。

## 3. 必须保留的产品与安全边界

Studio 仍是纯前端、本地优先产品，迁移不改变以下约束：

- 用户的文档、PDF、图片、Markdown 内容及附件不得上传到服务端、日志、Cookie 或第三方服务。
- 不增加账户、云存储、远程文件转换、AI 处理或遥测上传能力。
- 文件系统访问始终以用户明确授权为前提；取消、拒绝授权和浏览器不支持必须有可理解的回退。
- 每个功能的数据存储使用独立 IndexedDB 数据库或明确的命名空间与版本策略，禁止用“最近文件”功能跨工具保存文件内容。
- Worker、Object URL、Canvas、iframe、编辑器实例与临时缓冲区在成功、失败、取消、路由切换和组件卸载时均须释放。
- Office 继续同源自托管 OnlyOffice、SDKJS、x2t WASM 与字体；不使用第三方在线 iframe。
- PWA/Service Worker 的 scope、缓存名和更新策略必须以 Studio 为唯一来源，避免旧项目或 Office 资源污染其他路由缓存。

## 4. 重构与编码原则

1. **按产品目标重新设计。** 先定义每项能力的用户任务、输入输出、错误反馈、隐私提示和路由位置，
   再实现代码；不得因旧组件存在而保留不合理的流程或界面。
2. **先评估、后重写。** 迁移每个功能前，逐项将旧实现标记为“保留行为并重写”“可复用的纯逻辑”
   或“废弃”。重复状态、跨层耦合、无法释放资源、隐私边界不清、性能差和体验不一致的实现必须重写。
3. **功能等价不是代码等价。** 保持已承诺的本地处理、格式支持、授权和导出行为；其余实现、页面结构、
   状态管理与组件组织以 Studio 的统一架构为准。
4. **代码必须清晰且有必要的注释。** 使用严格 TypeScript、单一职责、明确命名、统一错误模型与资源
   生命周期。涉及浏览器兼容性限制、隐私约束、异步队列、文件格式差异、Worker/iframe/WASM 清理等
   非显而易见逻辑，必须用中文注释说明原因和不变量；不为可直接读懂的代码添加重复性注释。
5. **不迁入辅助遗留物。** 不复制旧构建产物，也不迁入与最终功能无关的旧文档、测试、夹具、脚本和资源；
   运行必需资源与法律合规声明除外。
6. **一次只重构一个功能域。** 每完成一个功能域，即按其验收条件在 Studio 验证；旧项目继续作为可用回滚基线。
7. **待办是唯一进度记录。** 每完成一件事情，立即在本文第 8 节勾选对应待办；发现新增工作时，先补充
   待办及验收条件再实施。未完成验证的事项不得勾选为完成。
8. **以可回滚发布取代一次切换。** 旧域名与 Studio 并行运行，确认稳定后再调整导航、Canonical 或重定向。

## 5. 分阶段执行计划

### 阶段 A：建立 Studio 基线

创建可独立运行的 Vue 3 + Vite 静态应用，接入 Vue Router、统一 TypeScript、pnpm、ESLint、
Prettier 与基础设计令牌。实现首页、主导航、路由懒加载、隐私页、捐赠页和错误边界，但不迁移
业务处理代码。

验收条件：Studio 可独立开发、类型检查、Lint、格式检查和静态构建；首页访问时不请求四类大型编辑器资源。

### 阶段 B：迁移 Image

Image 体量相对小、依赖边界清晰，适合作为首个迁移对象。将工具定义、浏览器图像处理逻辑和
Vue 视图迁入 `features/image/`，改用 Studio 统一布局、路由、错误提示和下载资源清理工具。

验收条件：全部现有图片工具在桌面和窄屏可用；批量、取消、下载与异常文件路径通过浏览器验证；
不出现网络上传请求。

### 阶段 C：迁移 Markdown

迁移编辑器、文件系统服务、工作区、预览、搜索 Worker、Mermaid、知识图谱与导出。将 Monaco、
Mermaid、导出依赖全部改为路由级按需加载，保持未命名草稿、授权目录、历史与对象 URL 的清理逻辑。

验收条件：可新建、打开、保存、恢复和导出 Markdown；授权目录与无授权草稿路径均通过真实浏览器验证；
远程图片 CORS 回退与本地文件处理行为保持既有承诺。

### 阶段 D：迁移 PDF

先迁移 `core/pdf/` 中纯处理逻辑和错误映射，再将工具页面、队列、预览、取消、下载与 SEO 说明
迁入 Studio 路由。PDF.js Worker、字体和预览资源采用 PDF 专属的按需加载策略。

验收条件：所有已公开工具在正常、损坏、超限和取消路径均通过定向测试；关键工具完成真实浏览器导出验证；
静态路由、帮助和隐私页面生成正确。

### 阶段 E：迁移 Office

Office 最后迁移。先完成旧 `office/` 的完整构建，以及 DOCX、XLSX、PPTX、CSV 的“打开 → 编辑 →
保存 → 重新打开”浏览器验收，再抽取会话队列、转换器、编辑器宿主和最近文档元数据逻辑。

OnlyOffice SDKJS、字体和 x2t WASM 迁移到 `public/office-assets/`，所有绝对资源路径、WASM
加载地址、编辑器 iframe 生命周期和 PWA 资源路径必须逐项改造与复测。

验收条件：四种首发格式均能在 Studio 独立路由下完成完整回环；路由切换不会遗留 iframe、
Object URL、Worker 或编辑器实例；Studio 首屏不加载 Office 资源。

### 阶段 F：整站联调与切换

统一跨功能入口、设计令牌、可访问性、隐私文案、浏览器兼容性说明、错误分类与统计边界。随后在
预发布环境进行并行发布、性能测试和回归；确认后再更新旧站导航与搜索引擎信号。

初期只从旧站指向 Studio 对应路由；Canonical、Sitemap、301 重定向和旧域名下线必须在流量、
索引和回滚方案确认后单独决策与执行。

## 6. 迁移顺序与依赖关系

```text
Studio 基线
    ├── Image
    ├── Markdown
    ├── PDF
    └── Office（依赖旧 Office 格式回环验收）
             ↓
      整站性能、安全、可访问性与发布联调
             ↓
      旧站导航切换 → SEO/重定向决策 → 旧项目退役
```

Image、Markdown 和 PDF 可以在完成 Studio 基线后交错推进，但它们对公共组件、设计令牌、
浏览器资源清理工具的修改必须通过同一套接口评审。Office 不能以未验收的旧实现为起点迁入。

## 7. 质量门槛与发布策略

每个功能迁移完成前至少满足：

- TypeScript 严格类型检查、Lint、格式检查通过；旧项目测试代码、夹具和报告不迁入 Studio。
- 在真实浏览器中验证桌面与窄屏；涉及文件处理时覆盖正常、取消、损坏或不支持文件的路径。
- 使用浏览器网络面板确认无文件内容上传、无意外第三方转换请求，且编辑器依赖仅在对应路由加载。
- 检查路由切换后的 Worker、对象 URL、iframe、内存与缓存释放情况。
- 完成 Studio 静态构建，并在目标服务器部署前执行实际 Nginx 配置检查和预发布冒烟测试。

每次发布保留上一版 Studio 静态产物与四个旧站产物。若某个 Studio 功能出现问题，导航可以单独
回退到对应旧域名，不影响其余三个功能。
